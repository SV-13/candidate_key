# REVIEW.md

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `list_employees` — pagination offset | The offset uses `page * page_size`. Since pages start at 1, page 1 incorrectly skips the first page of results. | `GET /employees?page=1&page_size=2` returns `EMP0003` and `EMP0004` rather than the first two employees, `EMP0001` and `EMP0002`. | Pending: calculate the offset as `(page - 1) * page_size` and add a regression test. |
| 2 | `list_employees` — filtered count | `total` is calculated using `count_documents({})`, ignoring the department filter applied to `items`. | `GET /employees?department=Sales&page=1&page_size=2` returns `total: 6`, although only two seeded employees belong to Sales. The faulty offset also makes `items` empty. | Pending: count using the same filter `q` as the listing query. |
| 3 | `list_employees` — sort order | The query does not explicitly sort by `emp_code` ascending, as required by the API contract. | The endpoint can return results in MongoDB's natural order, which is not a guaranteed API sort order. Test with records inserted in a different order. | Pending: sort by `emp_code` ascending in MongoDB before applying pagination. |
| 4 | `list_employees` — pagination validation | `page` and `page_size` do not enforce the required bounds: `page >= 1` and `1 <= page_size <= 100`. | `GET /employees?page=0&page_size=100` and `GET /employees?page=1&page_size=101` both return `200`, rather than `422`. | Pending: add FastAPI query constraints and test the invalid boundaries. |
| 5 | `create_employee` — duplicate creation race | A duplicate check followed by an insert is not atomic. Concurrent requests can both pass the check and insert the same `emp_code`. The starter also does not create the required unique index. | Send parallel employee-creation requests using the same `emp_code`; the contract requires exactly one `201` and the rest `409`. | Pending: create a unique index on `employees.emp_code` at startup and translate duplicate-key errors to `409`. |
| 6 | `EmployeeIn` / `create_employee` — request validation | The Pydantic model does not enforce the contract's field constraints, including employee-code format, lengths, email format, shift-time format, valid `joined_on`, and different shift start/end times. | Submit malformed values such as an invalid employee code, email, date or time, or identical shift start and end; the starter can accept values that should receive `422`. | Pending: add Pydantic field constraints and validation for `joined_on` and the shift-time relationship. |
| 7 | `create_employee` — `created_at` storage | `datetime.now()` creates a naive local datetime. PyMongo treats a naive datetime as UTC, so on an IST-configured machine the stored instant is shifted forward by 5 hours 30 minutes. | After creating `EMP900001`, MongoDB showed `2026-10-12T00:54:47.611000+00:00`, while current UTC at inspection was `2026-10-11T19:26:00.084620+00:00`. The approximately 5.5-hour difference is consistent with local IST being stored as UTC. | Pending: create an aware UTC datetime, store that instant, and test the stored value against UTC. |
| 8 | `create_employee` — `created_at` response format | The endpoint returns `created_at` as a datetime string instead of epoch milliseconds. | The actual `POST /employees` response included `"created_at":"2026-10-12T00:54:47.611265"`; the contract requires an integer epoch-millisecond value. | Pending: serialize `created_at` to integer epoch milliseconds and add a response-format test. |
| 9 | `punch_in` — employee lookup | The endpoint does not return `404` when `emp_code` does not identify an employee; it later indexes `emp["shift_start"]` when `emp` is `None`. | `POST /attendance/punch-in` with `{"emp_code":"EMP9999"}` returned `500 Internal Server Error`; the contract requires `404`. | Pending: check for a missing employee immediately after lookup and raise `HTTPException(404, ...)`. |
| 10 | `punch_in` — timestamp conversion | `datetime.fromtimestamp()` without an explicit timezone converts the instant to machine-local time and returns a naive datetime. PyMongo then treats that value as UTC when storing it. | With `TZ=Asia/Kolkata`, the instant `2026-07-06T04:10:15Z` converted to naive `2026-07-06 09:40:15`; storing that naive value as UTC shifts the instant by 5 hours 30 minutes. | Pending: convert epoch milliseconds to aware UTC datetimes and use timezone-aware PyMongo reads. |
| 11 | `punch_in` — whole-second truncation | The incoming instant is not truncated to whole seconds before calculations and storage, as R1 requires. | Submit a valid `punched_at` with a non-zero millisecond fraction; the starter conversion preserves a fractional second instead of storing the truncated whole-second instant. | Pending: normalize the timestamp once at the API boundary and use the same normalized datetime for calculations and storage. |
| 12 | `PunchInIn` / `punch_in` — status validation | `status` is a plain string, so values outside `PRESENT`, `WFH` and `ON_DUTY` are accepted. | A punch-in request with `{"emp_code":"EMP0001","status":"ABSENT"}` passes model validation even though punch-in must reject this status with `422`. | Pending: use a presence-status enum/type restricted to `PRESENT`, `WFH` and `ON_DUTY`. |
| 13 | `PunchInIn` — timestamp validation | `punched_at` is an ordinary optional integer without strict typing or epoch-millisecond bounds. Coercible values and out-of-range values are not rejected as required. The truthiness check also treats zero as if the timestamp were omitted. | Test a string, an integral float, a boolean, a seconds-looking number below `100000000000`, an out-of-range value, and `punched_at=0`; these should be rejected with `422`, not coerced or replaced with the current time. | Pending: use strict integer validation with the contract's minimum and maximum, and distinguish `None` from numeric zero. |
| 14 | `punch_in` — concurrent duplicate requests | The endpoint checks for an existing `(emp_code, date)` record before inserting, which is vulnerable to a race when two requests arrive together. The starter does not create the required unique compound index. | Send 20 simultaneous punch-in requests for the same employee and attendance date. The contract requires exactly one `201` and the remaining requests to receive `409`. | Pending: add a unique index on `(emp_code, date)` at startup and handle duplicate-key errors as `409`. |
| 15 | `compute_late_minutes` — grace boundary | Elapsed time is floored to whole minutes before the 10-minute grace period is checked. | For a 09:30 shift, the original helper returned `0` for a punch-in at `09:40:01`, whereas R2 requires `10`. | Implemented: compare elapsed whole seconds against 600 using strict `>`, then return elapsed whole minutes. Regression tests cover the grace boundary. |
| 16 | `compute_late_minutes` — overnight shift | The original helper reconstructs shift start on the punch-in's calendar date instead of using the correct overnight shift start. | For a 22:00–06:00 shift, a 00:30 punch-in returned `0` instead of `150` late minutes. | Implemented: calculate the attendance date and shift bounds, then calculate lateness against the actual aware shift-start instant. Regression tests cover the overnight case. |
| 17 | `compute_overtime` — timezone awareness | Subtracting a naive punch-out datetime from a timezone-aware shift-end datetime raises `TypeError`. | The original helper raised `TypeError: can't subtract offset-naive and offset-aware datetimes` for a naive punch-out and an aware shift end. | Implemented: use consistent aware UTC instants for shift bounds and calculations. Regression testing covers the calculation helpers. |
| 18 | `compute_overtime` — overnight shift | Shift end is constructed on the attendance date even when the shift crosses midnight. | For a 22:00–06:00 shift on 6 July, a 06:30 punch-out on 7 July returned `1470` overtime minutes instead of `30`. | Implemented: use `get_shift_bounds()` to place an overnight shift end on the following day. Regression tests cover the overnight threshold. |
| 19 | `compute_overtime` — minimum threshold | The original helper awarded overtime for any positive number of minutes after shift end, even when fewer than 30 whole minutes had elapsed. | A punch-out five minutes after shift end returned `5`, but R3 requires `0`. | Implemented: return overtime only when at least 30 whole minutes have elapsed. Regression tests cover 29:59 and 30:00 boundaries. |
| 20 | `compute_work_hours` — rounding | Built-in float rounding does not satisfy the required decimal half-up rule for all values. | The original helper returned `0.12` for 450 seconds and `2.67` for 9630 seconds; the required half-up results are `0.13` and `2.68`. | Implemented: calculate from whole integer seconds using `Decimal` and `ROUND_HALF_UP`. Regression tests cover both rounding traps and the half-day boundary. |
| 21 | `GET /attendance` — database pagination and memory use | The endpoint loads all matching attendance documents into Python, sorts them in memory, and only then slices one page. | With approximately 100,000 matching records and `page_size=20`, it still loads all matching records rather than letting MongoDB sort and paginate. | Pending: apply filters, sort, skip and limit in MongoDB, and count the filtered records separately. |
| 22 | `GET /attendance` — sort tie-breaker | The endpoint sorts by `date` descending only and omits the required `emp_code` ascending tie-breaker. | Two records on the same date have no contractually guaranteed employee-code order. | Pending: sort by `date` descending and `emp_code` ascending in MongoDB. |
| 23 | `GET /attendance` — internal identifier leaked | The endpoint converts MongoDB `_id` to a response field named `id`, even though the contract says attendance records are addressed by `(emp_code, date)` and `_id` must remain internal. | Attendance responses contain an `id` field derived from the MongoDB ObjectId. | Pending: omit `_id` and do not expose a replacement `id` field in attendance responses. |
| 24 | `GET /attendance` — timestamp response format | Raw MongoDB datetime values are returned through regular datetime serialization rather than as epoch milliseconds. Timestamp values nested in `history`, including `history[].at` and `history[].changes` punch-time values, also require conversion. | Inspect a record with `punch_in`, `punch_out` or history entries; the contract requires integer epoch milliseconds at every instant-valued API field. | Pending: convert all top-level and nested instant fields to epoch milliseconds when building the response. |
| 25 | `GET /attendance` — query validation | `status` is accepted as an arbitrary string, and date filters are not validated as calendar dates or checked to ensure `date_from <= date_to`. | Requests such as `GET /attendance?status=INVALID` or a reversed date range are not reliably rejected with `422`. | Pending: validate status against the defined enum, validate ISO calendar dates, and reject reversed ranges with `422`. |
| 26 | `health` — database readiness check | The endpoint always returns `{"status":"ok"}` without pinging MongoDB. | After `docker stop attendance-mongo`, `GET /health` still returned `HTTP/1.1 200 OK` with `{"status":"ok"}`. The contract requires `503` when MongoDB is unavailable. | Pending: ping MongoDB in the health handler and return `503` if the database cannot respond. |

## Behaviours checked but not classified as defects

- `GET /` and `GET /favicon.ico` return `404`. These are not treated as defects because the API contract does not require a root page or favicon endpoint; `/health` is the specified readiness endpoint.
